# Native pgBackRest / GCS trial — 27 September 2026

**Exact-set recovery passed; production adoption remains blocked.** The maintainer-operated JSON Keys
trial established useful native recovery behavior, with a material limitation: restoring a
soft-deleted dependency did not make it readable at the original repository-time cutoff.
The decision and remaining work belong to [#190](https://github.com/a-novel/infra/issues/190).
This report changes no runtime, IAM, backup schedule or production format.

## Observations

Repository `native-20260927`, stanza `json-keys`, database system identifier `7690306691413745679`.
The full set was `20260927-200643F`; its differential was
`20260927-200643F_20260927-200942D`. The source committed four distinguishable stages.
Successful restores checked row identities, the nonsuperuser `proof_reader` role and a real
`uuid-ossp` call, then stopped PostgreSQL cleanly.

| Case                                        | Observed result                                                                                                                                           |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native GCS backup and WAL archiving         | Completed with attached writer instance credentials and TLS verification.                                                                                 |
| Full / differential / named PITR            | SQL contained exactly stage 1 / stages 1–2 / stages 1–3; PITR used `proof_before_stage4`.                                                                 |
| Interrupted full upload                     | Copy progress and a partial object were observed; process-group kill returned 137. The completed catalog retained only the earlier full and differential. |
| Historical selection before dependency loss | `--repo=1 --repo-target-time="2026-09-27 20:35:40+00" --type=immediate` restored stages 1–2.                                                              |
| Aged full-backup dependency removed         | The same selection failed with exit 55, naming the missing full bundle. No server was started.                                                            |
| Recovery identity                           | Writer disabled; stopped VM switched to recovery identity, confirmed through metadata. Source PostgreSQL remained stopped.                                |
| Native GCS object repair                    | Recovery identity restored the exact soft-deleted generation with a create-only precondition; size and CRC matched.                                       |
| Original repository cutoff after repair     | Still failed with exit 55 for the same dependency.                                                                                                        |
| Explicit original differential after repair | `--set=20260927-200643F_20260927-200942D`, without a repository cutoff, restored stages 1–2 and the expected database identity, role and extension.       |

The deleted object was `backup/json-keys/20260927-200643F/bundle/1` below the repository prefix.
The differential manifest referenced that full bundle. Original generation `1790539605844244` was
soft-deleted at `2026-09-27T20:56:59.518Z`. Native restore produced generation `1790545410010137`
at `2026-09-27T21:43:30.018Z`, with the same 2,705,807 bytes and CRC32C `s32VFw==`.

This is consistent with the documented distinction between a
[repository-time view](https://pgbackrest.org/command.html#command-restore/option-repo-target-time)
and [native object restoration](https://docs.cloud.google.com/storage/docs/soft-delete): the repaired
live object has a later timestamp. The observed failure applies to this version and tested sequence;
it is not a claim that every historical-selection scenario fails. The operator explicitly selected
the original differential for the successful comparison; no automatic fallback changed the target.

`info` reported an OK catalog while the bundle was missing. Catalog health is not proof that a
dependency chain can restore. Source files remained intact during the recovery checks and were
deleted only in cleanup, so this is not a source-disk-loss drill.

## Adoption proposal

Retain pgBackRest as the candidate owner of physical backup, WAL, dependency tracking, verification
and expiry. Use its service-packaged executable and native GCS support; do not add a Go backup engine,
second catalog, or object reconstruction service. The [offline comparison](../pgbackrest/README.md)
and live results justify continuing evaluation, not a drop-in production replacement.

The proposed smallest integration is per-service native configuration on the existing database host,
with WAL archiving and declarative systemd backup units/timers. This avoids a second remote backup
coordinator. The host owner still manages mounts, credentials, process lifecycle and readiness.
The implementation must establish scheduling, shutdown and monitoring behavior before activation;
neither pgBackRest's lock nor a timer is evidence that all service operations are serialized.

Extend the existing recovery record only with the physical format's service/database identity,
exact runtime image and native set/target binding. pgBackRest owns its dependency inventory.
HCL owns bucket policy and IAM; the existing service boundary owns admission and operator approval.
Recovery uses an isolated empty target and separate management-side identity, with writers quiesced
and outcome validation before service exposure. Application rollout rollback must not restore data.

The custody decision remains open: the current logical uploader is create-only, while this trial's
writer could read and delete its selected repository's objects. Versioning, retention and soft delete
do not make that equivalent. Explicit-set recovery of repaired bytes also differs from recovering an
unchanged historical repository view. **No automatic fallback may remove a failed cutoff or choose a
different set.** Accept a precisely bounded repair contract separately, or reject this design; do not
hide the difference behind more tooling.
